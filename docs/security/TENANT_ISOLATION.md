# Tenant Isolation Strategy

Principle: **EF Core global query filters are one layer, never the security boundary.** Isolation is enforced at four independent layers; a bug in one must not expose data.

## Layers
1. **Request authorization.** The active tenant is chosen per request (`X-Tenant-Id` header / route). It is verified against `tenant_members` on every request; the JWT carries the user identity only and is never the authority for tenant access. Suspended tenants and removed members fail closed.
2. **Application scope.** A single `ITenantContext` (scoped) holds the verified tenant. Tenant-owned repositories/queries require it. There is no ambient default tenant: if it is unset, tenant-owned queries throw.
3. **EF Core global query filters** on every `ITenantOwned` entity, plus write-side checks (SaveChanges interceptor rejects inserts/updates whose `TenantId` differs from the context).
4. **SQL Server Row-Level Security** (D-010; mechanism revised by D-016). A `SECURITY POLICY` with FILTER and BLOCK predicates (an inline, schema-bound table-valued function comparing `TenantId` to `SESSION_CONTEXT(N'tenant_id')`) covers every tenant-owned table. The application connects with a login that is not the owner and has DML-only permissions, so it cannot alter policies. The tenant is set with `sp_set_session_context ... @read_only = 1` each time a connection is opened for a request or job (EF Core connection interceptor), so queries cannot change it. With no tenant set, the predicates return no rows. **This must be proven by tests before it is relied on:** (a) connection pooling never carries one tenant's context into the next request, (b) FILTER and BLOCK predicates stop cross-tenant reads and writes with EF filters disabled, (c) only the owner/migration login can change policies. Microsoft's RLS documentation also warns that a user who can run arbitrary queries may infer protected data through side channels, so the app login must never be given ad hoc query access, which is another reason raw SQL is restricted. Migrations run under the separate owner login.

## Specific surfaces
- **Raw SQL:** allowed only inside Infrastructure through `ITenantSqlExecutor` (parameterized, runs on a connection whose tenant session context is already set so RLS applies). `FromSqlRaw`/`ExecuteSqlRaw` anywhere else fails an architecture test. Raw SQL must still state the tenant predicate explicitly; RLS is the backstop.
- **Background jobs / worker:** every job payload carries `TenantId`. The job runner creates a new DI scope, sets `ITenantContext` from the payload (and re-validates the tenant is active), then sets the session context. A job with no TenantId fails closed and goes to dead-letter. Cross-tenant maintenance jobs (usage aggregation, token health) iterate tenants one at a time with the same scoping.
- **Administrative operations:** PlatformAdmin endpoints live in a separate route group and policy, use an explicit `IAdminScope` (never `IgnoreQueryFilters` ad hoc), run under a dedicated DB role with narrow privileges (tenant metadata, plans, health), expose no message content by default, and write an audit log entry per action. `IgnoreQueryFilters` is banned outside an allowlisted class (architecture test).
- **Tenant switching:** switching is just sending a different verified `X-Tenant-Id`; no server-side "current tenant" session state. SignalR connections join groups only after membership verification and are re-validated on tenant change; membership removal disconnects the user from that tenant's groups.
- **Caches and Redis:** all keys are prefixed by tenant ID. **Vector search:** every retrieval query (`VECTOR_DISTANCE`) includes the tenant predicate and runs under RLS.
- **Files/knowledge storage:** paths include the tenant ID; access goes through tenant-checked services.

## Required tests (Phase 1 onward)
Cross-tenant read, update, delete and list by ID guessing; user in tenant A sending tenant B's ID; removed member loses access; suspended tenant blocked; job without TenantId rejected; filter bypass attempts; RLS verified with filters disabled (proves layer 4 alone blocks access); raw SQL helper scoping; admin endpoint access control; architecture tests for banned APIs.
SQL Server specific: pooled-connection context isolation test; BLOCK predicate rejects an insert/update that targets another tenant; app login cannot ALTER a security policy.
